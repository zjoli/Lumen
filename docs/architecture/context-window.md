# Lumen 上下文窗口设计

状态：首版已实现；本页保留完整目标设计，实际边界见配套实现方案第 14 节。设计日期：2026-11-04。实现更新：2026-11-05。

本文定义模型上下文窗口的分区、预算、装配、缓存、Skill 和压缩策略。与 [Agent Loop](agent-loop.md)、[知识存储、检索与同步](knowledge-storage.md) 配套；现有代码与本提案的差异见第 12 节。

插件调度、状态归属、请求封存和持久化协议见 [上下文管理的插件集成与实现决策](context-management-implementation.md)。

## 1. 目标与边界

上下文管理负责让模型在有限窗口内获得继续当前任务所需的信息，同时控制信息损失、调用费用和等待时间。优先级依次为：指令与任务正确性、请求合法和可恢复、任务完成质量、成本与延迟。缓存命中率是诊断指标，不能单独作为优化目标。

区分三个对象：

| 对象 | 保存什么 | 生命周期 |
| --- | --- | --- |
| Transcript | 用户原话、完整 assistant 消息、工具交互、显式上下文控制记录 | 追加归档，不因压缩删除或改写 |
| Working Context | 本次实际发送给模型的规则、状态、摘要、Skill、消息和资料 | 有预算的请求投影，可重建 |
| Memory | 学习目标、知识对象、学习证据、长期偏好等 | 独立存储、按来源更新、按需注入 |

聊天摘要不自动成为长期记忆；模型对学习程度的猜测不能直接替代有证据的学习状态。Lumen 既有学习记录与纠错链继续作为学习状态来源。

定义一个 **窗口周期（epoch）**：从新会话或一次成功压缩后开始，到下一次成功压缩或显式重建为止。同一周期内，已发送的前缀保持稳定，新消息、状态变化和资料追加到尾部。

## 2. 把上下文看作一个窗口

### 2.1 窗口分区图

下图展示周期开始时的逻辑布局。A 包含工具声明，其实际位置由 Provider 的消息协议和渲染规则决定；H 是容量预留，不是发送给模型的文本。

```text
模型上下文总容量 W
┌──────────────────────────────────────────────────────────────┐
│ A. 核心规则与工具定义                                        │
│    Agent 职责、行为规则、工具 schema、来源解释规则             │
├──────────────────────────────────────────────────────────────┤
│ B. 工作区规则与 Skill 目录                                   │
│    工作区约定、语言、可用 Skill 的名称/描述/定位信息            │
├──────────────────────────────────────────────────────────────┤
│ C. 当前任务与学习状态快照                                    │
│    目标、约束、计划、用户纠正、相关学习状态及证据               │
├──────────────────────────────────────────────────────────────┤
│ D. 历史摘要                                                 │
│    已完成事项、决策、失败尝试、未解决问题、证据与历史定位       │
├──────────────────────────────────────────────────────────────┤
│ E. 仍在使用的 Skill                                         │
│    正文、必要依赖、版本、执行进度                             │
├──────────────────────────────────────────────────────────────┤
│ F. 近期完整交互                                             │
│    用户消息、assistant 消息、完整工具交互、状态变化和资料       │
├──────────────────────────────────────────────────────────────┤
│ G. 当前新增内容                                             │
│    最新用户输入、选中内容、当前引用、最新检索结果或工具结果     │
├──────────────────────────────────────────────────────────────┤
│ H. 预留空间                                                 │
│    本次模型输出、下一步工具结果增长、安全余量                  │
└──────────────────────────────────────────────────────────────┘
```

**分区用于表达职责和计算预算，不表示每次请求都把同类内容重新归组。** 周期内产生的 Skill 加载、规则更新、状态变化、资料都按发生顺序追加；G 在后续请求中自然成为 F。下一次压缩时才重新形成 C、D、E 的周期起始布局。

### 2.2 每个区域的策略

| 区域 | 保存内容 | 进入与更新策略 | 压缩和退出策略 |
| --- | --- | --- | --- |
| A 核心规则与工具 | Agent 职责、指令优先级、固定行为、工具名称/说明/schema | 按版本生成；工具稳定排序；同一周期保持不变 | 不做有损摘要；精简由开发者修改模板完成；工具集不兼容变化时显式重建 |
| B 工作区与目录 | 工作区规则；Skill 名称、描述、来源和定位信息 | 周期开始加载快照；更新以带版本的新消息追加；目录有独立预算 | 保留有效规则；删除已停用目录项；大量 Skill 改用目录搜索 |
| C 任务与学习状态 | 当前目标、范围、硬约束、偏好、计划、已确认结论、相关学习证据 | 从用户消息、任务记录、学习记录生成快照；变化追加 delta | 下一周期合并有效状态；保留最新纠正及来源；结束的任务只保留必要交接信息 |
| D 历史摘要 | 旧交互中的决策、进展、失败原因、未解问题和原文引用 | 新会话可为空；压缩成功后生成；周期内不反复改写 | 有界更新；重要事实可回查原文；过期过程移到可检索历史 |
| E 活跃 Skill | 当前任务需要的 SKILL.md、必要引用、版本与步骤状态 | 激活时按需读取并追加；内容相同不重复加载 | 压缩时重新附加仍需执行的指导；已完成 Skill 只留结果与来源 |
| F 近期交互 | 最近完整交互单元，包括工具、资料与状态变化 | 按原顺序追加，已发送内容不回写 | 优先保留最近交互；旧单元整组进入摘要；工具调用与结果不能拆开 |
| G 当前内容 | 未覆盖的新用户请求、steering、引用、检索结果或工具结果 | 先计数与限额，再追加；资料带来源、版本和裁剪标记 | 当前用户目标和纠正不因超预算静默丢弃；可恢复资料先缩小范围 |
| H 预留 | 输出额度、工具增长、安全余量 | 根据模型限制、请求设置和工具类型计算 | 不参与摘要；不能为容纳旧历史而耗尽 |

### 2.3 C 与 D 的区别

C 回答“现在要做什么、必须遵守什么”；D 回答“之前做过什么、为什么形成现在的状态”。同一个事实设定一个主要归属，避免在两区完整重复。

例如“用户每天只有 30 分钟”属于 C 的有效约束；“原计划被缩短，因为用户改为每天 30 分钟”只在确有交接价值时写入 D。用户后来改为 45 分钟，C 采用 45 分钟，并保留对应纠正来源；旧值在历史中可查。

## 3. 窗口预算

### 3.1 预算公式

```text
W = Provider 给出的模型上下文容量
O = 本次最大输出预留（含模型要求纳入的推理/输出额度）
T = 下一步工具结果增长预留
S = 协议开销和计数误差余量
B = W - O - T - S

I = 实际渲染后输入 token 数，包括工具定义和所有区域文本
请求必须满足 I <= B，并同时满足厂商独立的输入、输出限制
```

T 是留给下一步的增长余量；已经进入消息的工具结果必须计入 I。即使预留了 T，每次请求前仍需重新验证。模型或厂商对推理 token 的计量方式由 Provider 适配，禁止假定所有厂商使用同一公式细节。

优先使用厂商计数接口或匹配模型的 tokenizer；无法准确计数时采用保守估算，结合返回 usage 校准。预算包含角色包装、来源标签、工具 schema、Skill 和多模态内容；不能只统计消息正文。模型容量未知时使用已配置的保守上限，并在观测中标明估算。

### 3.2 初始配置示例

下例假设 W = 128,000 tokens，O = 8,000、T = 8,000、S = 4,000，因此 B = 108,000。数值是 Lumen 初始调参示例，不是厂商通用限制，也不表示应主动填满窗口。

| 区域 | 参考额度 | 性质 |
| --- | ---: | --- |
| A 核心规则与工具 | 6,000 | 预计占用；超额需精简或缩小工具集，不能截断 schema |
| B 工作区与 Skill 目录 | 4,000 | 目录可缩小；有效规则不能静默截断 |
| C 当前状态 | 4,000 | 压缩过程描述，保留有效约束 |
| D 历史摘要 | 8,000 | 摘要目标上限 |
| E 活跃 Skill | 12,000 | 按需加载；不能靠截断隐藏必要步骤 |
| F 近期交互 | 68,000 | 主要弹性区域 |
| G 当前新增内容 | 6,000 | 普通请求参考额度；其中自动检索初始预算沿用 4,000 |
| 合计输入预算 B | 108,000 | 各区共享未使用额度，发送前检查总量 |

上述额度不是固定槽位。G 超额时可以借用 F 等区域的空间；有效硬约束或显式引用超额时，先减少自动检索和旧历史。Skill 正文超过 E 时可以借用剩余额度或读取其明确划分的阶段，不能任意截掉尾部并宣称已完整加载。

### 3.3 水位与触发

初始策略：

- `I < 0.80 × B`：正常追加；持续限制新资料和工具输出。
- `0.80 × B <= I <= B`：在下一个安全边界尝试压缩，目标 `I_after <= 0.55 × B`。
- `I > B`：禁止发送；先释放可选资料、执行压缩或要求缩小不可再分的大输入。

80% 和 55% 为可配置起点；实际应按任务成功率、输出增长和延迟调整。A/B/C/E 等必要内容较大时，55% 可能不可达；只要释放了足够后续空间并满足硬预算即可接受，记录目标未达原因。

任务阶段完成、主题切换、用户执行 `/compact` 也可以触发压缩。缓存过期本身不强制触发压缩；若摘要需冷读取全量历史，应结合预计后续轮数衡量收益。

## 4. 一次请求如何装配

只有 ContextWindowPlugin 统一决定最终顺序与预算。检索、Skill、学习状态模块贡献候选上下文项，不能各自在系统提示前部反复插入文本。

```text
1. 读取 transcript、最近有效 checkpoint、周期内 context journal
2. 固定本次 transcript/context journal 水位，纳入已收到的 steering
3. 收集状态变化、显式引用、Skill 激活和检索候选
4. 去重、校验来源与 revision、限制新内容大小
5. 从当前 epoch 恢复原前缀，按时间追加新内容
6. 计算含工具定义的输入预算
7. 若超水位，在安全边界生成并校验新 checkpoint
8. 将可见 Custom/context 项显式转换成模型消息
9. 校验指令存在、工具配对、引用范围和最终预算
10. Provider 编码请求；完成后记录 usage 和渲染摘要
```

新的用户消息到达时不能落在压缩覆盖范围之外却被丢弃。压缩只覆盖步骤 2 固定的水位，提交前检查父 checkpoint 未变；并发追加留在下一窗口尾部。一个 session 同时只有一个上下文写入者，并行分支保持独立 checkpoint。

自动检索以新的用户问题、明确的检索调用或知识 revision 变化为触发条件，不在每个工具续轮重新执行完全相同的检索。阶段性 retrieval failure 允许无自动资料继续；显式要求必须引用的资料不可用时，应明确说明缺失。

检索内容按照既有 L0 摘要、L1 概览、L2 正文分层读取。片段至少包含对象 ID/URL、revision 或抓取标识、章节或范围、是否裁剪。外部资料始终标记为参考数据，不能因此获得系统指令优先级。

逻辑分区不决定消息权限。A 使用系统/开发者指令和工具声明；B 按可信配置来源映射。C/D 保留原消息的来源和优先级，摘要不能把用户要求或外部原文升级为系统规则。E 的工作流权限由 Skill 来源与既有策略确定。F/G 中真实工具交互保持厂商要求的角色与调用 ID；检索资料使用明确标记为数据的内容块。Provider 编码不得为了方便把所有区域合并进 system。

## 5. 缓存策略

### 5.1 周期内追加，周期间重建

```text
周期 1 请求 1：[A B C D E] [user1]
周期 1 请求 2：[A B C D E] [user1 assistant1] [user2 reference2]
周期 1 请求 3：[A B C D E] [user1 assistant1 user2 reference2 ...] [新内容]

压缩边界

周期 2 请求 1：[A B C' D' E'] [保留的近期交互] [新内容]
```

A/B 未变化时，压缩后的请求仍有机会复用这一部分前缀；C 之后通常需要建立新缓存。压缩的价值按总成本与质量评价，不要求保住旧会话的全部缓存。

具体规则：

1. 核心模板、工具定义、目录使用确定性排序和稳定渲染；固定部分不放每轮时间戳、随机 ID 或最新阅读位置。
2. 周期内文件、任务状态、语言偏好、工作区规则变化以新消息表达，声明新值替代什么旧值；不能为缓存保留过期约束的效力。
3. 已发送的资料保持原历史快照。源文件变化时追加新 revision 的片段；必要时重新读取，不能把旧引用悄悄替换成新内容。
4. Skill 激活、模式变化和状态 delta 追加到尾部，避免修改系统提示。
5. 工具集、模型、渲染模板等无法兼容的变化允许显式建立新周期。正确性优先于缓存，不能通过保留失效工具声明绕过变化。
6. 不在每轮重写摘要或移动同一段历史；可恢复资料的批量移除优先放到压缩边界。

### 5.2 摘要请求与厂商适配

通用摘要请求优先复用当前模型、原系统提示、工具声明和历史前缀，在末尾追加摘要指令；摘要运行禁止实际工具执行。若改用其他模型或重写前缀，必须计入缓存损失与摘要质量差异，不能只比较摘要模型单价。

摘要请求也有独立预算：计入新增摘要指令、摘要输出额度和计数余量后，仍须满足模型容量及厂商输入限制。若待压缩输入本身已经装不下，先移出可恢复资料，或按合法交互边界分块提取，再生成最终摘要；每个子请求都单独计数。每块最多两次尝试，分块数量受本次固定覆盖范围与执行预算约束；任何子块失败就保留旧 checkpoint 并进入失败降级，禁止把超限历史直接交给摘要接口。

Provider 暴露缓存能力、缓存参数、usage 和兼容性信息，Context 层不写死厂商字段。自动缓存、显式断点、TTL、缓存写入价格由具体适配器负责；网关不支持时降级并记录原因。请求内容一致也不保证命中，缓存可能过期、路由变化或不受该连接方式支持。

原生 compaction 作为后续能力接入，必须保留原生返回窗口及不透明项，遵守对应协议，不能当普通文本任意裁剪。不能假设压缩项可跨厂商或模型迁移；迁移使用 transcript 和可读 checkpoint 重建。

## 6. Skill 管理

### 6.1 发现与目录

优先兼容 `SKILL.md` 的名称、描述及资源目录；Lumen 的启用范围、来源与版本等元数据放在 registry 中，不要求第三方 Skill 改写格式。

每项至少记录 `skill_id`、名称、描述、来源、入口、内容 hash、启用范围、资源定位方式。`skill_id` 带来源命名空间，同名项不自动合并；用户显式选择优先，选择结果可检查。

启动时只加载目录信息，正文留在窗口外。目录超预算时先精简展示描述；规模更大时使用 Skill 搜索工具按需发现，并提示目录并非完整清单。目录渲染保持稳定，新增与启停变化以版本记录进入 journal，在明确边界刷新快照。

### 6.2 加载与执行

```text
discovered → selected → loaded → active → completed / inactive
                                  │
                                  └─ 压缩后仍 active → rehydrate
```

- 显式调用直接解析目标；隐式选择依据适用场景与边界，必要时使用目录搜索。
- 激活时加载 `SKILL.md`，资源按步骤需要读取。脚本保存在磁盘，通常注入执行结果和定位信息。
- 以 `skill_id + 渲染内容 hash` 去重。带参数或动态内容的 Skill 还需记录实际参数和渲染结果，原文件 hash 相同不代表内容相同。
- 同一版本正文已在窗口中时，只追加简短激活或进度记录。
- 文件更新产生新版本并明确替代关系，旧历史仍保留；是否在当前任务采用新版本有显式记录。
- Skill 只提供工作流；执行权限仍由现有权限策略处理，不能从摘要中的“已允许”推导新的权限。

### 6.3 压缩时处理 Skill

活跃 Skill 记录包含版本、可恢复正文、已读依赖、当前步骤、完成项、未完成项。新周期重新附加后续仍需要的指导，并保留进度；关键指导不能只改写成“继续遵循某 Skill”。必要正文不能放入预算时，减少可选 Skill/资料，或将任务切到 Skill 明确划分的阶段。

已完成或失活的 Skill 不再重新附加正文，在 D 中只保留产物与决策。任务完成时先追加失活记录，不立即从旧历史删除正文；到压缩边界再释放其占用。

## 7. 压缩策略

### 7.1 第一级：进入窗口前减少体积

这一层不改写已发送历史：

- 搜索返回有界候选、摘要和定位，按需读取正文。
- 大文档按章节或范围读取；明确引用的原文保留对应精确范围。
- 工具原始输出完整保存到 artifact，模型可见结果只放关键字段、失败信息、预览和读取引用。
- 使用内容 hash 与来源范围去重；重复注入只追加必要定位。
- 即使工具原始结果巨大，也先生成合法、可恢复的有界工具结果，避免一条结果立即填满窗口。

### 7.2 第二级：在边界清理可恢复内容

当需要释放空间时，优先处理已完成工作的详细日志、重复片段、已被新 revision 替代的原文和已完成 Skill 正文。已发送内容的移除会改变前缀，因此默认与下一层合并成一次 checkpoint 重建；不每轮删除少量旧内容。

移除后留下“来源、范围、结论、何时需要重读”的短记录。有无法重建的证据、当前失败细节或后续必要原文时，不应仅因年代较久就移除。

### 7.3 第三级：摘要旧交互，保留近期原文

压缩单位是 **完整交互组**：通常从一条用户消息开始，包含相关 assistant 响应、工具调用与结果，以及必要的后续响应。最低协议单元是“一条 assistant 的全部工具调用及其对应结果”，禁止拆分。

初始保留策略：优先保留最近两个完整用户交互组以及当前未完成组，同时设近期 token 预算。若单个旧交互组过大，可把其已完成的完整工具单元连同上下文压入摘要；最新用户意图、纠正和未完成工具单元必须保留。组数是质量偏好，token 硬预算始终生效。

触发流程：

1. 选择切分边界，固定覆盖水位；A/B、有效硬约束、当前请求和未完成工具组列为保留项。
2. 收集旧摘要、被覆盖的新交互以及重要事实的原文依据。
3. 从确定来源构建 C；使用摘要模型构建 D，并提取 Skill 进度。用户硬约束保留原句或精确字段和值。
4. 重新附加活跃 Skill，保留近期交互与水位后的新消息。
5. 验证来源、必保项、工具配对和预算；生成候选 checkpoint。
6. 原子提交 checkpoint 与 journal 水位后才切换 epoch；取消或失败继续使用旧 checkpoint。

### 7.4 历史摘要格式

```yaml
schema_version: 1
scope: 当前任务与覆盖的交互范围
completed:
  - 已完成事项、产物引用、验证结果
decisions:
  - 结论、原因、证据引用、已知限制
failed_attempts:
  - 尝试、失败证据、是否仍值得重试
open_questions:
  - 尚未确定的信息、验证方式
next_steps:
  - 下一步及依赖
evidence_refs:
  - message_id / object_id + revision + range / artifact_id
coverage:
  - 已覆盖与未覆盖的范围
```

C 单独保存 `goal`、`scope`、`constraints`、`preferences`、`plan`、相关 `learning_state` 和来源；活跃 Skill 由 E 的结构化记录保存。摘要文本中区分用户要求、确认事实、模型推测、失败结论与待验证内容，不能把推测压成事实。

摘要只更新旧摘要加增量容易逐轮漂移。每次压缩都从原始来源刷新硬约束、当前目标、关键数值和活跃步骤；其他长期摘要采用增量更新，发现证据缺失或矛盾时回查 transcript。不能仅因信息在旧摘要里出现过就视为已确认。

### 7.5 验证与失败降级

接受 checkpoint 的最低条件：

- A/B 必要指令存在，当前目标与最新用户纠正保留。
- 重要事实有可解析来源；明确标识无法恢复的证据。
- 没有孤立工具结果、缺失结果的历史调用或被截断的调用参数。
- 活跃 Skill 的必要指导与未完成步骤能够继续执行。
- 最终输入满足预算，且获得有意义的净空间收益。

若摘要不够短，可用同一覆盖输入重试一次更小目标；首版每次触发的最终摘要最多生成两次，分块提取另按第 5.2 节限制，不能无限压缩摘要。低收益参考阈值为 `max(1,000 tokens, 0.05 × B)`，小窗口应另行配置；目标是防止反复付费却不释放空间。

失败处理：

| 情况 | 行为 |
| --- | --- |
| 摘要失败，但原输入仍满足 B | 保留旧 checkpoint；允许请求继续，下一安全边界重试 |
| 资料太大 | 减少自动检索、正文范围或工具预览，原始内容保存在可读取位置 |
| 当前输入加必要规则本身超过 B | 不静默裁剪用户请求；说明实际容量问题，采用分段输入或用户选择范围 |
| 硬预算超限且摘要仍失败 | 停止本次模型请求，保留会话与候选产物，提供重试或切换任务范围的入口 |
| 压缩后立刻再次触发且释放量不足 | 识别主导占用项，不重复循环摘要；转为缩小单项或任务分段 |
| 取消或崩溃 | 不提交候选 checkpoint；恢复最近完整检查点及其后的追加记录 |

## 8. 持久化与恢复

### 8.1 记录边界

沿用 `sessions/<session-id>/<segment-id>.jsonl` 归档格式，不改写已关闭片段。新增显式上下文控制记录可使用现有 `AgentMessage::Custom`，但必须带 schema_version，并在恢复时明确识别；它们不自动作为普通聊天文本发送。

建议记录种类：

- `context_epoch`：周期 ID、父周期、覆盖水位、模板/规则版本、模型兼容信息。
- `context_checkpoint`：C/D/E 的可恢复内容、近期交互 ID、对应 journal 水位与校验 hash。
- `context_item`：自动注入资料、规则更新、Skill 激活及状态 delta 的内容或持久引用。

checkpoint 必须具备完整恢复所需的自包含文本或耐久引用。需要归档的工具原文和引用快照可使用既有内容寻址 `assets/`；不能只引用 `.lumen/` 下会被删除的缓存文件。大文件继续遵守知识仓库的附件与同步限制，超限内容需明确标记仅本机可恢复。

这些内部记录使用白名单转换：应进入模型的 checkpoint/上下文项转为带来源的正常内容块；纯 UI 和遥测记录不进入模型。不能继续把所有 Custom 一律过滤，也不能把所有 Custom 不加区分地发送。

### 8.2 Context journal 与可重建缓存

自动检索等资料不作为用户/assistant 消息重复归档，也不修改旧 transcript；它们通过独立的、可检查的 context item 记录本次请求投影。首次被模型使用前持久化必要内容与顺序；相同内容通过 hash 复用。

`.lumen/context/<session-id>/` 保存 checkpoint 快速索引、渲染缓存和 token 估算，可以删除后从归档记录重建。缓存 TTL、厂商 response ID 和本机路径不能作为恢复唯一依据。

这是对现有“自动检索只产生临时请求投影”的补充：不重复保存知识正文为用户消息，但显式保存模型看到的版本与投影顺序。实现时需同步更新知识存储文档的第 7.2 节。

### 8.3 恢复顺序

1. 校验会话片段及控制记录，选择当前分支最近有效 checkpoint。
2. 恢复 A/B 版本、C/D/E、保留交互及对应 context journal。
3. 按顺序追加覆盖水位以后的 transcript 和 context item，避免摘要与原文重复覆盖。
4. 校验 Skill、资料引用和厂商兼容性；当前源文件变化以新 revision 更新表达。
5. 重新计数；模型变化或 checkpoint 不兼容时，从可读状态与原始 transcript 重建窗口。

未找到有效 checkpoint 时，从 transcript 和源资料重建；不能把丢失 checkpoint 当作丢失完整会话。多设备会话分支不按时间戳强行拼成单一工具交互，用户选择分支或显式生成合并交接摘要。

## 9. 学习场景示例

用户正在学习数据库事务：

| 区域 | 初始内容 | 一轮学习后的变化 |
| --- | --- | --- |
| A | 导师行为、回答与工具规则 | 保持不变 |
| B | 中文工作区、练习与复盘 Skill 目录 | 保持不变 |
| C | 目标：理解隔离级别；每天 30 分钟；已掌握原子性 | 追加“每天改为 45 分钟”的纠正及“快照读仍需练习”的证据 |
| D | 已讲解脏读；并发示例的结论与引用 | 周期内不修改，等下一次压缩更新 |
| E | 当前练习 Skill、已完成第 1 题 | 追加第 2 题进度，正文不重复加载 |
| F | 最近问答、题目、回答与评估结果 | 保留本轮完整交互 |
| G | 用户提问：“可重复读是否仍会有幻读？”；相关章节 | 追加提问及来源明确的资料，下一轮归入近期历史 |
| H | 输出、工具增长与余量 | 每轮重新计算 |

达到水位后，旧示例全文可移出窗口，D 保留“结论适用的数据库实现、证据和未确认之处”；C 合并为每天 45 分钟，并保留尚未解决的学习目标；E 恢复仍需完成的练习步骤。不能只保留一句“用户学过事务”，也不能把一次答对直接写成“已熟练掌握”。

## 10. 模块与接口职责

沿用 AgentPlugin / before_request 入口，Loop 只负责调度，不承担检索、学习状态或厂商策略。

| 模块 | 职责 |
| --- | --- |
| ContextWindowPlugin | 唯一窗口装配入口，管理周期、合并候选、预算、触发压缩、校验投影 |
| TokenCounter / ModelCapabilities | 完整请求计数、模型容量、输出限制及误差声明 |
| CompactionService | 生成可读摘要或调用原生 compaction，返回候选，不直接改写 transcript |
| SkillRegistry / SkillLoader | 发现、选择、版本、去重、资源读取和恢复 |
| Retrieval / LearningState | 提供有来源、有预算的候选资料与状态变化 |
| Session / ContextStore | 显式 context journal、原子 checkpoint、来源与恢复 |
| ModelProvider | 厂商协议、缓存配置、原生状态与 usage 归一化 |
| TUI / Telemetry | 展示区域占用、压缩结果、来源和成本，不改写上下文 |

Context item 至少带 `id`、逻辑区域、来源、内容/hash、token 估算、revision、适用范围、必要性、替代关系和生命周期。checkpoint 至少带 `id`、父 checkpoint、分支、覆盖水位、区域内容/引用、模型/模板版本与校验信息。

只保存一份权威 transcript，通过显式 checkpoint 和 journal 派生当前窗口；插件不能维护不可检查的隐藏消息副本。具体 Rust 结构在实现阶段确定，本文不承诺现有接口已包含这些能力。

## 11. 观测与验收

提供 `/context` 展示 A–G token 占用、总预算、H 预留、估算方式、当前 epoch、活跃 Skill、最近压缩前后大小及降级原因。`/compact` 显式触发，支持给出保留重点；`/skills` 查看来源、版本、激活和恢复状态。

遥测记录输入、输出、缓存读写 token、实际价格下的费用、首 token 延迟、压缩耗时、压缩次数、重新读取资料量。缓存字段不支持时显示 unavailable，不当作 0 命中。聚合命中率使用总缓存读取 token / 对应总输入 token，不平均每轮百分比。

验收关注行为，不只检查摘要变短：

1. 同一周期新增消息不改变旧的渲染前缀；新增检索与 Skill 不重写系统提示。
2. token 统计覆盖工具和 Skill；长单条消息也能触发预算处理。
3. 最新用户纠正、任务约束在连续多次压缩后仍能从来源正确恢复。
4. 摘要和活跃 Skill 实际进入 Provider 请求，UI-only Custom 不进入。
5. 压缩边界不拆分工具交互；大型工具输出有完整 artifact 和合法有界结果。
6. 取消、摘要失败、零收益、硬超限都能收敛，不无限重试或丢失当前输入。
7. 重启后恢复相同的窗口内容与顺序；删除 `.lumen/` 后仍能从归档重建。
8. Skill 同内容不重复加载，更新有版本，失活后在下一压缩周期释放。
9. 注入资料保留来源与 revision；旧源失效或分支冲突时不会伪装成当前事实。
10. 使用实际长学习任务回放，比较任务连续性、事实保留、总费用和延迟；模拟测试不能证明服务端缓存一定命中。

## 12. 现状与实施顺序

### 12.1 实现前的问题记录（已由首版处理）

- 旧 CompactionPlugin 只截取文本，摘要 Custom 被 Loop 过滤；现保留显式 legacy 路径，应用改用统一协调插件。
- 检索资料曾被拼入 system；现通过 Collect 提供候选，在预算内追加并记录实际注入版本。
- Provider 已有容量、prepare/stream_prepared、估算与 usage；原生 compaction 仍为后续可选后端。
- SessionRuntime 已实现 journal、检查点、文件恢复与工作区归档；工具声明继续按名称排序。

### 12.2 分阶段交付

| 阶段 | 交付内容 | 完成标准 |
| --- | --- | --- |
| P0 正确传递与预算 | 白名单转换 Custom；固定规则保留；完整工具组；计数、预留和硬预算；工具结果限额 | 不丢摘要、不发送超预算或非法工具消息 |
| P1 统一装配与检查点 | ContextWindowPlugin；检索改为候选；稳定追加；通用摘要、journal、checkpoint 和恢复 | 连续运行和重启都能保留任务意图与窗口顺序 |
| P2 Skill 与学习状态 | 目录预算、按需读取、去重、活跃状态、压缩恢复；接入学习记录 | 长任务中的工作流和学习进度可持续 |
| P3 厂商优化与调优 | 缓存参数、usage、原生 compaction、任务回放和水位调参 | 以质量与实际总成本验证优化效果 |

第一版采用可读摘要作为跨 Provider 的基础恢复机制；原生压缩作为可选后端，不能替代本地会话与来源记录。
